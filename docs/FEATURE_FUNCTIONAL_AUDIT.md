## Method and coverage definition

The template scan found **197 static `<button>`, `<input>`, `<select>`, and `<textarea>` elements** across the application shell, views, and component templates. The matrix below inventories those controls grouped by their mounted page/component; dynamic controls rendered from data (device rows, incident rows, map markers, palette entity results) are represented in their parent feature row. A control group can contain multiple elements and its status is a group-level status. A static element count is not the same as a runtime mounted-element count.

Statuses mean:

- `WORKING`: the inspected path has a real action/state outcome and the important behavior has a targeted automated test.
- `PARTIALLY_WORKING`: a code path exists, but the whole control group lacks a browser/role/network interaction test, or one member has a known limitation.
- `BROKEN`: inspected handler fails or returns misleading behavior.
- `UNIMPLEMENTED`: no real behavior exists and it has not been represented as intentionally disabled.
- `INTENTIONALLY_DISABLED`: the UI states the boundary and does not claim the action completed.
- `NOT_VERIFIED`: no adequate source path or test evidence was found.

## Audited findings and fixes in this phase

- Settings controls previously had no page controller. They now persist validated, non-sensitive preferences, set the actual sound manager gain/tone, start/stop one ambience source, and keep voice alerts opt-in and rate-limited to newly changed priority incidents. Mute/disable cancels queued speech.
- Integration sandbox previously had display-only controls. It now has a safe local command set and an allowlisted, simulation-labeled JSON request explorer. It does not execute shell commands or make outbound requests.
- Dashboard speed and refresh controls were bound before their lazily mounted view existed. They now use delegated handlers, enforce Operator/Admin on speed changes, disable during the authoritative request, restore acknowledged values on error, and only show success after a successful resync/command response.
- Dashboard AI action had duplicate listeners in `TrafficEngine` and `SignalsController`; the duplicate opener was removed. The dashboard Reports quick action now navigates to Reports without keeping the report controller active on Dashboard.
- Signals green-split sliders now restore the last acknowledged canonical value when the command is rejected. Adapter updates tolerate absent `dataset` in non-DOM test stubs.
- Emergency cancel no longer marks every fixed sample ID as canceled or swallows errors; it targets active state records and surfaces failures.
- Removed the former static hardcoded incident CSV rows. The report export now serializes current incidents with safe CSV escaping and simulation provenance.
- Fixed report preview generation that called a missing progress method before entering `try`, leaving the modal stuck at 0%. Progress is now bounded and rendered, and failures reach the error state. Preview creation is logged/labeled as a simulation preview rather than an already downloaded PDF. The PDF download action no longer also triggers `window.print()` through a duplicate listener.
- Removed dashboard static progress fills and demo uptime/camera/sensor/latency literals. Health values render from available StateStore/telemetry values or `—`; the latency sparkline stays hidden without samples. The analytics page no longer flashes hardcoded vehicle/speed figures before its model snapshot is ready.
- Map uses one context menu. The unused hardcoded ambulance popup was removed. Clipboard failure is reported; map incident-area filtering is explicitly stated as unavailable.

## Deliberate boundaries and known gaps

- The three Integration endpoints are local demonstration endpoints backed by current simulator state; they are not government/SITS APIs.
- No physical APILL, CCTV, vehicle, emergency dispatch, or field telemetry connection is created. `SIMULATION_ONLY` remains the operational boundary.
- The map's incident-per-area filter is not implemented; UI communicates that limitation and does not report a successful filter.
- Several multi-step modals and interactions have source-path coverage but still need real browser tests, especially report PDF download/print, focus return, incident/emergency workflows, device configuration acknowledgement, signal rejection recovery, CCTV lifecycle, entity palette focus, and role-specific control visibility.
- The reports screen creates a current-state snapshot; there is no claim of persistent report history.
